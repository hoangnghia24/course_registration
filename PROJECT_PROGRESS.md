### Security decisions

- Password hashes are owned only by Serverpod Auth tables. The application
  `users` table references the Serverpod `authUserId` and never duplicates a
  password hash.
- Self-registration receives the `student` scope. Lecturer and admin scopes
  must be assigned through a future authorized administration workflow.
- SQLite stores session metadata only. JWT and refresh credentials are managed
  by `FlutterAuthSessionManager` and platform secure storage.

### Business rules

- GPA uses a weighted 4.0 scale and is rounded to two decimals.
- The greatest attempt number replaces previous attempts for cumulative GPA.
- Failed attempts affect GPA and attempted credits; only passed attempts earn
  credits.
- Read repositories are remote-first and fall back to last synchronized Drift
  payloads when the server is unavailable.

### Database changes

  `course_opening_requests` and `registration_history`.
- Added `course_prerequisites` and `course_equivalents` to support eligibility
  rules that were specified outside the primary Phase 4 table list.
- Added unique and lookup indexes for semester classes, registrations,
  prerequisites and equivalents.
- Applied migration `20260930183339078-phase-4-registration` to development
  PostgreSQL successfully.
- Upgraded Drift to schema version 3 with current-semester, open-class and
  registered-course caches.

### Validation and consistency

- Registration uses a single transaction and locks both student and
  course-class rows before the final credit, capacity and eligibility checks.
- Checks prerequisites and equivalent courses, schedule overlap, 25-credit
  maximum, major/training program, duplicate courses and available capacity.
- Cancellation validates ownership and semester status, decrements capacity
  safely and records history.
- The 10-credit minimum is progress guidance because enforcing it per insert
  would make the first registration impossible.

### Validation and security

- Every endpoint requires lecturer scope; class-specific APIs additionally

  be reduced below current enrollment.

- Actual schedules and all non-rejected proposals participate in lecturer
  conflict detection.
- Lecturer schedule proposals remain `PENDING`; approval is reserved for a
  later authorized administration phase.

### Security and workflow

- Admin APIs require an authenticated, active administrator and granular
  permissions; an empty permission table enables initial bootstrap access.
- User removal is a soft disable. Disabled users are rejected by profile,
  student, registration, lecturer, and admin authorization paths.
- New lecturer classes remain closed until an admin approves them.
- Class approval/rejection and schedule publication run transactionally and
  create immutable audit records.
- Admin account creation links an existing Auth UUID and does not handle raw
  passwords.
